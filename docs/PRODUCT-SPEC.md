# 产品功能与要求规范

> 后续确认更新（2026-09-28）：品牌已定为demo，第3项前端方案与界面已确认冻结，见UI-001-BASELINE。下文v2草稿的未定名/待第3项表述保留其历史阶段；本次不扩大确认到其余开放架构或外部能力。

版本：UI-001 功能规范修订稿 v2，2026-09-28。用户已明确产品定位；本稿待审阅，技术栈、工程结构和前端基线尚未冻结。

## 1. 产品定义
**以 Codex 作为软件本体和核心运行能力，使用独立产品名称与品牌，在保留 Codex 工作能力的基础上加入视频生成。**

用户所说的“套壳”是本项目的产品方向：用户进入软件后使用的就是由 Codex 驱动的工作环境，编程、项目、会话、工具执行和审批构成软件主体；视频能力在同一产品内扩展。Codex 不再只是通用 AI 助手中的一个可选编程模块。

产品名称不叫 Codex，最终名称待定。独立命名不改变底层实际使用 Codex 的事实；产品说明、诊断和依赖信息应如实表达技术来源。本轮不进行产品命名、界面重排或技术栈替换。

“与 Codex 一样的能力”是完整产品的对齐目标，不能擅自缩减成聊天或代码生成。仅调用一个 Codex 模型、提供一个跳转入口或展示类似界面，都不足以满足该目标。

## 2. Codex 本体能力要求
以下是产品需求清单，不是当前已实现清单，也不是宣称每一项都由同一个官方接口直接提供。

| 能力域 | 必须达到的产品行为 | 对齐验收方向 |
| --- | --- | --- |
| 核心 Agent | 使用真实 Codex 运行能力理解任务、获取上下文、规划、调用工具、持续执行与处理失败 | 同一任务实际完成工具调用及结果交付；能观察过程、停止和继续，不以模拟回复验收 |
| 项目与工作区 | 选择项目、读取项目约束和文件、限定操作范围；支撑仓库/分支及隔离工作区工作流 | 在指定项目内执行，遵守项目规则，越界受控；不损坏其他项目 |
| 会话与上下文 | 创建、继续、恢复、重命名、组织会话，呈现消息、工具事件及任务状态 | 重启/中断后可恢复，执行记录可追溯；本地草稿与真实 Codex 会话明确区分 |
| 编程与文件 | 阅读、搜索、编辑代码，执行构建/测试，诊断错误和修复，审阅代码变更 | 文件、命令输出、差异与验证结果来自实际执行；失败可见 |
| 终端与进程 | 运行获准命令，查看输出及退出状态，停止任务并处理后台进程 | 命令范围、执行环境和结果可查，取消后不遗留失控进程 |
| 差异与版本管理 | 查看修改前后差异，支持审阅及获准的 Git 操作 | 能判断具体改了什么；不擅自提交、推送、丢弃或覆盖用户工作 |
| 审批与权限 | 将 Codex 请求和产品扩展操作纳入可见、可拒绝的审批流程 | 授权绑定目标、参数和有效期；拒绝、过期、参数变化阻止执行 |
| 多 Agent 与持续任务 | 对齐参考 Codex 中用户需要的分工、进度、协调、继续执行及任务管理能力 | 状态来自真实 Agent/任务，文件所有权和取消边界明确 |
| 工具与扩展 | 承接 MCP、技能及插件能力，展示来源、可用性、配置与权限 | 真实发现和调用；格式及宿主能力逐项确认，不把所有插件默认视为兼容 |
| 电脑与浏览器 | 保留目标工作流需要的本机/页面观察与操作能力 | 实际连接器提供可观察结果、明确目标及中止能力；不能因使用 Codex 就声称自动具备 |
| 模型与连接配置 | 保留用户选择模型中转的需求，与 Codex 运行方式、协议和能力要求共同核实 | 真实请求、流式事件、工具调用、错误和取消均可验证；不能把能返回文本当作完整兼容 |

### 能力对齐方法
- 以用户实际使用的 Codex 产品及确认的参考版本为对照，建立逐项对齐清单；参考版本尚未锁定，不能提前声称“完全一致”。上表是当前最低需求，不作为排除其他 Codex 能力的封闭清单。
- 每项记录：参考行为、复用的 Codex 能力、产品需补的宿主能力、依赖/限制、实现状态、验收证据。
- 状态至少区分：待核实、未实现、已实现待验证、已验证、存在差异；演示/模拟单独标注。
- 某项无法直接承接时，保留需求并说明缺口与补足方案，交用户决定；不得自行删减目标或把未实现包装为完成。
- 模型服务、账号能力、官方云服务与本机宿主功能分别核实。使用 Codex 核心不等于自动获得官方客户端所有功能和服务。

## 3. 视频生成扩展
视频是加在 Codex 本体工作流中的能力，能够通过会话调用，也能在软件内管理素材、任务与结果，不是与 Codex 相互割裂的另一个产品。

| 环节 | 功能要求 |
| --- | --- |
| 素材输入 | 引用用户图片、视频、音频及项目素材；保留原文件，明确每份素材用途 |
| 提示词与方案 | 利用会话上下文协助整理目标、生成参数和提示词；用户可查看、修改并保存 |
| 供应商调用 | 经确认的供应商提供真实视频生成；支持的输入类型、时长等以实际能力为准 |
| 提交与审批 | 提交前展示最终提示词、素材、参数、供应商及可获得的费用信息；付费操作再次确认 |
| 任务与失败 | 记录真实任务ID、运行状态、错误和重试；取消是否生效按供应商响应说明，不伪造进度 |
| 结果与追溯 | 在同一软件查看视频和相关产物，关联原会话/项目/素材与参数，输出另存，不覆盖原素材 |

具体视频模型、供应商和首批功能尚未确定，后续逐项细化。本次不自动增加剪辑时间线、直播等未提出的功能，不要求现在提供密钥，也不提交任何付费任务。

## 4. 复用边界与官方依据
已核实的官方信息支持“以真实 Codex 为核心构建自己的产品”：
- 官方 [Codex App Server 文档](https://learn.chatgpt.com/docs/app-server)将其定位为自有产品深度集成接口，包含认证、会话历史、审批和流式 Agent 事件。
- 官方 [Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)说明可复用的核心是 Agent 执行系统；CLI、app-server 和 SDK 提供集成途径，模型访问和托管服务仍是独立部分。

因此，App Server 是后续架构评审的有依据候选；本次只确认功能定位，不提前冻结接入方案。不能把这些资料解读成“整个官方桌面客户端已直接换名复用”或“官方全部服务已继承”。接入范围和需要补齐的宿主能力，留到下一项架构审阅逐项确定。

## 5. 当前实现与本次修改边界
当前已有独立 Windows 候选外壳：模块导航、系统目录选择、本地会话创建/切换/重命名、草稿保存与重启恢复。这些是工程准备，不满足完整 Codex 本体能力对齐验收。

当前尚未接入真实 Codex 运行时、模型中转、终端执行、差异读取、执行审批、电脑/浏览器控制、MCP、插件技能或视频供应商。界面必须如实标注。当前六域导航是既有候选界面，不代表用户已认可它作为最终产品结构。

本规范为四项中的第1项；用户随后已要求按此修改第2项架构，具体目标方案见ARCHITECTURE v2。界面、验收基线及运行代码仍保持原候选状态，待后续逐项审阅与实现；文档更新不代表运行软件已对齐。

## 6. 数据、安全与质量要求
- 用户项目和原始素材受保护；删除先列路径、数量、影响并等确认；付款、注册、发消息、账号权限修改执行前再次确认。
- 模型、网页、素材和插件内容不能自授权限。执行来源、审批和结果可追溯；用户可停止正在运行的任务。
- 凭据使用系统安全存储并脱敏，不进入源码、前端包、日志或交接。模型中转与视频供应商分别配置和验收。
- 当前本地草稿是 .local/app/sessions.json 明文数据，不是凭据存储；损坏数据不能静默覆盖。
- Windows 中文界面、键盘可达、加载/错误/未接入状态清楚。静态检查、构建、模拟、真实运行和供应商联调分别记录。
- 技术栈与界面需在同一可运行应用中共同验收，用户确认后一起冻结。功能定位的这次澄清不等于对现有架构或界面的确认。

## 7. 分期与完成口径
先审定本功能规范，再逐项审阅架构、界面与验收；随后围绕 Codex 本体建立能力对齐和接入任务，视频作为该工作环境的扩展推进。具体独立任务和依赖由 TASKS 统一管理，每项新功能使用新主会话。

骨架完成、Codex 本体接入完成、Codex 能力对齐完成、视频扩展完成是不同里程碑。只有对应真实功能和验证证据齐备才能标记完成，不能用本地草稿功能代替 Codex，也不能用供应商入口代替视频生成。
